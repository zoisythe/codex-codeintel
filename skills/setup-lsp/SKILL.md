name: setup-lsp
description: Configure, install or repair Codex CodeIntel language servers and project checkers for a project or explicitly requested global defaults. Use for setup tasks; ordinary coding with missing tools only needs a brief setup suggestion.
---

Set up working CodeIntel capabilities for the requested scope. The display name is **setupLSP** and invocation is **`$setup-lsp`**.

1. Identify scope and conventions. Default to the current project; modify `$CODEX_HOME/lsp-client.json` (default `~/.codex/lsp-client.json`) only when the user requests global setup. Read both existing configurations, applicable repository instructions, language manifests, package-manager/lock files, environments, build files and representative source files. Do not read or change Codex directory trust records. Use the absolute project directory as `workspace`.
2. Reuse explicit commands, nearest project environments and PATH tools, in that order. Check actual startup before replacing configuration. Repair/report a failing installed command at its current location; do not download another version as a fallback. Install missing tools within the chosen scope using the project's conventions: Python uses uv; Node respects the package manager and otherwise prefers pnpm. Reuse Rust toolchains and C/C++ build systems. If an installation fails, record the unavailable capability and continue independent languages. A system change outside the requested scope needs separate authorization; finish the other configuration work first.
3. Merge configuration using [configuration.md](references/configuration.md). Preserve unrelated settings and explicitly disabled capabilities; arrays replace rather than merge in the plugin. Put reusable defaults in global configuration only for global setup, and project directories, checker commands and coverage in project configuration. New configurations enable nonblocking `postToolUse="delta"` and `stop="errors"` feedback. Preserve existing automatic-off choices. Never enable `stopGate` automatically, and never put it in project configuration.
4. Cover the actual project using [languages.md](references/languages.md). Configure Python ty and Ruff independently, appropriate TypeScript LSP and type/lint checks for each package, Cargo workspace checks, and C/C++ compilation databases. Set coverage to the command's actual input set, including exclusions. If the C/C++ checker cannot emit supported JSON/SARIF, keep clangd capabilities and explain the project-check gap. A successful check of one source file does not establish whole-project coverage.
5. Verify capabilities through the installed plugin. Call `lsp_status` with `refresh=true` and representative paths; it only resolves tools and reports state. Run `check_diagnostics` for those paths, exercise a read-only navigation operation such as definition or symbols, and run `check_project`, following structured `next` until finished. Diagnose pending, failed or uncovered results. Do not count `command -v` or `--version` alone as completion. Use an isolated fixture when the user project lacks a usable representative; state that verification limit. Do not rename or format files unless the user's task authorizes those writes.
6. Report exact configuration paths changed, tools installed, verified capabilities, remaining gaps and recovery steps. Partial setup is useful: an unavailable checker never prevents ordinary editing or verification of other languages.

This skill is normally discoverable, but installation/configuration changes belong to setup, installation or repair requests. During ordinary coding, explain missing capability once and suggest `$setup-lsp`; continue the coding task without repeated installs, retries or a setup prerequisite.
